## 📜 Descrição

O Pulse Control é uma plataforma web de gestão socioeducacional desenvolvida em parceria com a Pulse Mais, ONG sem fins lucrativos que impulsiona jovens talentos de baixa renda a conquistar carreiras em tecnologia. Com mais de três anos de atuação e mais de 180 jovens formados e 75 empregados, a organização enfrentava um problema operacional crítico, os dados dos beneficiários estavam fragmentados em múltiplas planilhas isoladas, o que impedia uma visão consolidada da jornada de cada jovem e dificultava a prestação de contas a financiadores e parceiros.

O Pulse Control nasce para resolver essa fragmentação, estabelecendo uma fonte única de verdade (SSOT) sobre a trajetória de cada jovem atendido pela Pulse Mais. Como solução, a plataforma centraliza o cadastro completo dos beneficiários, dados pessoais, histórico de programas, frequência em aulas e eventos, evolução no framework próprio da ONG (Conectado → Capacitado → Transformado), indicadores de empregabilidade e acesso ao ensino superior. Adicionalmente, contempla um módulo de acompanhamento de mentoria, no qual mentores registram sessões e consultam informações dos jovens vinculados, e um prontuário digital de acesso exclusivo ao psicólogo, que armazena observações de saúde mental com visibilidade restrita para garantir a confidencialidade dos dados sensíveis.

A solução é estruturada em cinco perfis de acesso com permissões exclusivas, sendo eles a Coordenação, Gestão, Mentor, Psicólogo e Aluno, cada um com sua interface personalizada. O perfil de Coordenação é o centro operacional da plataforma, permitindo o registro de frequência, gestão de vínculos de mentoria, busca parametrizada por múltiplos filtros e visualização do perfil consolidado de cada jovem em uma única tela. Já o perfil de Gestão acessa um dashboard estratégico com indicadores de impacto que fortalecem a captação de recursos e a prestação de contas a doadores. Por fim, o Portal do Aluno permite que o próprio jovem acesse e atualize seus dados, tornando-o protagonista de sua trajetória.

No âmbito tecnológico, o sistema foi construído com TypeScript/Node.js/Express no back-end, HTML/CSS/JavaScript no front-end e banco de dados PostgreSQL via Supabase, seguindo padrões de desenvolvimento em camadas (models → repositories → services → controllers → routes) e respeitando os requisitos funcionais, não funcionais e regras de negócio do sistema. Por fim, ressalta-se que o desenvolvimento ocorre em sprints cadenciadas com validação periódica junto à equipe da Pulse Mais, garantindo aderência contínua às necessidades reais da organização.

## 📁 Estrutura de pastas

├── documentos/                 # Documentação completa do projeto
│   ├── wad.md                  # Web Application Document (WAD) — documentação técnica principal
│   ├── outros/                 # Documentos auxiliares (ex.: webapi-docs.html)
│   └── tests/                  # Suíte de testes automatizados (Jest + Supertest)
│       ├── *Service.test.ts    # Testes unitários das regras de negócio
│       ├── *Controller.test.ts # Testes de integração HTTP das rotas (Supertest)
│       ├── helpers.test.ts     # Testes dos helpers (validarCpf, calcularIdade, etc.)
│       └── setup.ts            # Setup do Jest (define DATABASE_URL de teste)
├── src/                        # Aplicação completa (projeto npm: back-end + front-end)
│   ├── node_modules/           # Dependências instaladas via npm (não versionadas)
│   ├── models/                 # Definições de tipos e interfaces TypeScript

│   │   ├── dashboard.html      # Tela de login e seleção de perfil
│   │   ├── alunos.html         # Lista e busca de jovens cadastrados
│   │   ├── perfil-aluno.html   # Perfil individual consolidado do jovem
│   │   ├── empregabilidade.html # Dashboard de renda e empregabilidade
│   │   ├── ensino-superior.html # Registro e acompanhamento de ensino superior
│   │   └── ...                 # Demais telas por perfil (mentor, psicólogo, aluno)
│   ├── server.ts               # Ponto de entrada (sobe o servidor HTTP)
│   ├── app.ts                  # Cria o app Express (rotas /api + estáticos do front)
│   ├── .env                    # Variáveis de ambiente (não versionado — solicitar ao time)
│   ├── .env.example            # Exemplo de variáveis de ambiente necessárias
│   ├── jest.config.ts          # Configuração do Jest (aponta para documentos/tests)
│   ├── tsconfig.json           # Configuração do compilador TypeScript
│   ├── tsconfig.build.json     # Configuração do build de produção (gera src/dist)
│   ├── package.json            # Dependências e scripts do projeto (npm)
│   └── package-lock.json       # Lock file das dependências (npm)

> **Atenção:** como o `package.json` está em `src/`, todos os comandos `npm` (`install`, `dev`, `test`, `build`, `start`, `migrate`) devem ser executados **a partir da pasta `src/`**.

Detalhamento das pastas principais:

- **assets**: armazena as imagens utilizadas na documentação do repositório, incluindo o logotipo do Inteli e as fotos dos integrantes referenciadas neste README.

- **documentos**: contém toda a documentação técnica do projeto e as evidências. O arquivo principal é o wad.md (Web Application Document), que registra a arquitetura da solução, os requisitos funcionais e não funcionais, os diagramas de banco de dados, os fluxos de cada módulo, o protótipo de alta fidelidade e os relatórios de testes. A subpasta `tests/` reúne a suíte automatizada.

- **src**: é o projeto npm completo e executável. O back-end está organizado em cinco camadas sequenciais — models (interfaces TypeScript de cada entidade), repositories (operações com o PostgreSQL via Supabase), services (regras de negócio, incluindo validação de perfil e controle de visibilidade), controllers (tratam o contrato HTTP) e routes (registram os endpoints REST). O `app.ts` também serve estaticamente o front-end de `view/` em produção.

- **src/view**: reúne todos os arquivos de interface da aplicação web. Cada tela corresponde a um arquivo .html auto-contido que importa o design system compartilhado (pulse.css) e a biblioteca de ícones Lucide. O arquivo pulse.css define os tokens de design (cores #003870, #33B458, #FFD927), os componentes reutilizáveis (sidebar, topbar, cards, badges, botões) e os padrões de responsividade da plataforma.

- **documentos/tests**: abriga os testes automatizados escritos com Jest e Supertest, organizados de forma plana (sem subpastas). Os arquivos *Service.test.ts cobrem as regras de negócio de cada vertical com os repositórios mockados; os arquivos *Controller.test.ts verificam o contrato HTTP das rotas via Supertest (sem abrir porta TCP e sem tocar o banco real). O setup.ts define uma DATABASE_URL fictícia para que o pool não falhe na inicialização — o banco real nunca é acessado nos testes.

## 🔧 Configuração para desenvolvimento e execução do código

### Pré-requisitos

- [Node.js](https://nodejs.org/) — versão 18 LTS ou superior
- [Git](https://git-scm.com/)
- Uma conta no [Supabase](https://supabase.com/) (ou acesso às credenciais do projeto via membro do time)
- Um editor de código, preferencialmente [VS Code](https://code.visualstudio.com/)

### Passo 1 - Clonar o repositório

Abra o terminal e execute:

```bash
git clone https://git.inteli.edu.br/graduacao/2026-1b/t29/g05.git
cd g05
```

### Passo 2 - Instalar as dependências

> **Importante:** o projeto Node (package.json, dependências, configs e `.env`) fica na pasta **`src/`**. Todos os comandos `npm` desta seção devem ser executados a partir de `src/`.

```bash
cd src
npm install
```

Isso instalará todas as dependências definidas no `package.json`, incluindo Express, TypeScript, Jest e as demais bibliotecas do back-end.

### Passo 3 - Configurar as variáveis de ambiente

Ainda dentro de `src/`, copie o arquivo de exemplo e preencha com as credenciais corretas:

```bash
cp .env.example .env
```

O arquivo .env exige apenas duas variáveis:

| Variável | Obrigatória | Descrição |
|----------|:-----------:|-----------|
| DATABASE_URL | Sim | String de conexão PostgreSQL do Supabase. No painel do Supabase: **Project Settings → Database → Connection string → URI** (use a porta 6543, do pooler). Formato: postgresql://postgres.<ref>:<senha>@aws-0-<região>.pooler.supabase.com:6543/postgres. |
| PORT | Não | Porta local da API (padrão 3000). |

> O acesso ao banco usa SSL automaticamente (ssl: { rejectUnauthorized: false }), compatível com o Supabase. Solicite a DATABASE_URL ao time por um canal seguro caso não tenha um projeto Supabase próprio.

### Passo 4 - Executar as migrations

```bash
npm run migrate
```

Esse comando (ts-node db/migrate.ts, a partir de `src/`) cria todas as tabelas caso ainda não existam. É **idempotente**: todo CREATE/ALTER é guardado por IF NOT EXISTS / verificação em information_schema, então pode ser executado mais de uma vez sem erro. Ao final imprime Migrate concluído com sucesso..

### Passo 5 - Executar o servidor de desenvolvimento

```bash
npm run dev
```

O servidor sobe em http://localhost:3000 (ou na PORT definida). Para confirmar que subiu, acesse http://localhost:3000/api/health — deve responder {"status":"ok"}. As rotas da API seguem o padrão /api/<recurso>.

### Passo 6 - Executar os testes

```bash
npm test                 # roda toda a suíte (Jest)
npm test -- --coverage   # roda com relatório de cobertura
```

A suíte é totalmente isolada (repositórios e pool mockados) — **não requer banco nem servidor no ar**. Os arquivos de teste ficam em `documentos/tests/`; o `jest.config.ts` (em `src/`) aponta para lá automaticamente.

### Passo 7 - Acessar o front-end (desenvolvimento)

Com `npm run dev` rodando, o próprio servidor já serve as telas: acesse **http://localhost:3000/** (redireciona para a tela inicial de login).

> Alternativamente, é possível abrir as telas de `src/view/` com a extensão **Live Server** do VS Code (http://localhost:5500). **Não abra os arquivos via file:// diretamente no navegador** — o back-end aceita apenas origens http(s)://localhost / 127.0.0.1 (política de CORS em `src/app.ts`); o protocolo file:// produz uma origem incompatível e as chamadas à API são bloqueadas. Mesmo sem a API no ar, a interface carrega com dados de demonstração (fallback mock).

### Passo 8 - Executar em modo produção

A partir de `src/`:

```bash
npm run build   # compila a aplicação (tsc → src/dist) e copia view → dist/view
npm start       # node dist/server.js
```

Em produção o próprio back-end serve o front-end estático: com o servidor no ar, acesse **http://localhost:3000/** (redireciona para a tela inicial) — não é necessário Live Server. A API continua sob http://localhost:3000/api.

### Passo 9 - Rodar com um banco de dados novo (do zero)

Se você for usar **seu próprio banco Supabase vazio** (em vez do banco do time), siga este roteiro.

**9.1 — Montar a `DATABASE_URL` correta (pooler)**

No painel do **seu** projeto Supabase: **botão `Connect` → aba `Connection string` → `Transaction pooler`** e **copie a URI inteira** (só troque `[YOUR-PASSWORD]` pela senha do banco). Cole em `src/.env`:

```
DATABASE_URL=postgresql://postgres.<SEU-REF>:<SENHA>@aws-<N>-<REGIAO>.pooler.supabase.com:6543/postgres
```

> ⚠️ **Não monte o host à mão** — copie do painel. Erros comuns:
> - **Usar a URL da API** (`https://<ref>.supabase.co`) como `DATABASE_URL`. Errado: essa é a API REST (Cloudflare); o driver `pg` precisa de uma string `postgresql://`.
> - **Cluster/região errados no host.** O prefixo (`aws-0`, `aws-1`, …) e a região variam por projeto; se não baterem, o pooler responde `tenant/user ... not found`.
> - **Usar a conexão direta** (`db.<ref>.supabase.co:5432`): hoje é IPv6-only e costuma dar `ENOTFOUND`/`ETIMEDOUT` em redes IPv4. Prefira sempre o **pooler na porta 6543**.
> - No pooler o usuário é `postgres.<ref>`; na conexão direta é apenas `postgres`.

**9.2 — Criar o schema**

```bash
cd src
npm run migrate   # deve imprimir "Migrate concluído com sucesso."
```

Se imprimir o sucesso, a conexão está correta. A migration cria apenas o **schema** (sem dados) — o banco fica vazio.

**9.3 — Subir a aplicação**

```bash
npm run dev
```

**9.4 — Popular os usuários iniciais**

Um banco vazio não tem `usuario`, então a tela de login fica sem perfis. Com o servidor rodando, crie os usuários de demonstração. Perfis válidos: `Gestao`, `Coordenacao`, `Psicologo`, `Mentor`, `Aluno`.

**PowerShell (Windows):**

```powershell
# Equipe (Gestor, Coordenador, Psicólogo, Mentor)
Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios" -Method Post -ContentType "application/json" -Body '{"nome":"Gabriela Almeida","email":"gabriela.almeida@pulse.org","perfil":"Gestao"}'
Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios" -Method Post -ContentType "application/json" -Body '{"nome":"Joana Moura","email":"joana.moura@pulse.org","perfil":"Coordenacao"}'
Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios" -Method Post -ContentType "application/json" -Body '{"nome":"Diego Goia","email":"diego.goia@pulse.org","perfil":"Psicologo"}'
Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios" -Method Post -ContentType "application/json" -Body '{"nome":"Daniel Souza","email":"daniel.souza@pulse.org","perfil":"Mentor"}'

# Aluno Henrique Vieira — 2 passos: o perfil "Aluno" exige um jovem vinculado.
# 1) cria o jovem (id_usuario = um usuário já existente; aqui o Gestor criado acima)
$gestor = Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios"  # lista os usuários
$idResp = ($gestor | Where-Object { $_.perfil -eq "Gestao" } | Select-Object -First 1).id
$jovem  = Invoke-RestMethod -Uri "http://localhost:3000/api/jovens" -Method Post -ContentType "application/json" -Body (@{ nome="Henrique Vieira"; email="henrique.vieira@pulse.org"; telefone="11999990000"; id_usuario=$idResp } | ConvertTo-Json)
# 2) cria o usuário Aluno vinculado ao jovem recém-criado
Invoke-RestMethod -Uri "http://localhost:3000/api/usuarios" -Method Post -ContentType "application/json" -Body (@{ nome="Henrique Vieira"; email="henrique.aluno@pulse.org"; perfil="Aluno"; id_jovem=$jovem.id } | ConvertTo-Json)
```

**Bash / curl (Linux, macOS, Git Bash):**

```bash
API=http://localhost:3000/api
curl -s -X POST $API/usuarios -H "Content-Type: application/json" -d '{"nome":"Gabriela Almeida","email":"gabriela.almeida@pulse.org","perfil":"Gestao"}'
curl -s -X POST $API/usuarios -H "Content-Type: application/json" -d '{"nome":"Joana Moura","email":"joana.moura@pulse.org","perfil":"Coordenacao"}'
curl -s -X POST $API/usuarios -H "Content-Type: application/json" -d '{"nome":"Diego Goia","email":"diego.goia@pulse.org","perfil":"Psicologo"}'
curl -s -X POST $API/usuarios -H "Content-Type: application/json" -d '{"nome":"Daniel Souza","email":"daniel.souza@pulse.org","perfil":"Mentor"}'

# Aluno (2 passos): cria o jovem usando o id do Gestor e depois o usuário Aluno
ID_RESP=$(curl -s $API/usuarios | grep -o '"id":[0-9]*' | head -1 | grep -o '[0-9]*')
ID_JOVEM=$(curl -s -X POST $API/jovens -H "Content-Type: application/json" -d "{\"nome\":\"Henrique Vieira\",\"email\":\"henrique.vieira@pulse.org\",\"telefone\":\"11999990000\",\"id_usuario\":$ID_RESP}" | grep -o '"id":[0-9]*' | head -1 | grep -o '[0-9]*')
curl -s -X POST $API/usuarios -H "Content-Type: application/json" -d "{\"nome\":\"Henrique Vieira\",\"email\":\"henrique.aluno@pulse.org\",\"perfil\":\"Aluno\",\"id_jovem\":$ID_JOVEM}"
```

> Observações:
> - O perfil **Aluno** sempre exige `id_jovem` (vínculo a um jovem existente) — por isso o jovem é criado antes.
> - A criação de um jovem exige `nome`, `email`, `telefone` e um `id_usuario` responsável (registrado na auditoria).
> - No Windows, `curl` é alias do `Invoke-WebRequest`; use `curl.exe` para a sintaxe `-X/-H/-d`, ou prefira os comandos `Invoke-RestMethod` acima.

**9.5 — Acessar**

Recarregue **http://localhost:3000/** (ou o Live Server). A tela inicial agora lista Gabriela, Joana, Diego, Daniel e Henrique. A partir daqui, tudo que você cadastrar pela interface é gravado nesse banco.

## 🔌 Endpoints disponíveis

Todas as rotas têm prefixo /api. A descrição detalhada (RFs/RNs) está no WAD; a tabela abaixo é o resumo para validação rápida.

| Método | Path | Descrição |
|--------|------|-----------|
| GET | /api/health | Healthcheck ({ status: "ok" }). |
| GET / POST | /api/usuarios | Lista / cria usuários. |
| GET / PUT / DELETE | /api/usuarios/:id | Consulta / atualiza / remove usuário. |
| GET / POST | /api/jovens | Lista (com filtros categoria, status_global, programa) / cria jovem. |
| GET / PATCH / DELETE | /api/jovens/:id | Consulta / atualiza / inativa jovem. |
| GET | /api/jovens/:id/perfil-completo | Perfil consolidado (categorias, frequência, empregabilidade, ensino superior, mentorias). |
| GET / POST | /api/jovens/:id/categoria | Histórico / mudança de categoria. |
| GET / POST | /api/jovens/:id/empregabilidade | Histórico / registro de empregabilidade. |
| GET / POST | /api/jovens/:id/ensino-superior | Histórico / registro de ensino superior. |

## 🔒 Decisões de escopo

- **Autenticação não foi implementada neste MVP.** O sistema não possui login, emissão/validação de token (JWT) nem middleware de sessão; a variável SESSION_SECRET mencionada em artefatos anteriores **não é utilizada** e não precisa ser configurada. Esta foi uma decisão consciente de escopo do grupo para a entrega, priorizando o CRUD completo, os dashboards e os relatórios.
- **O que isso significa para o avaliador:** as rotas podem ser chamadas diretamente (via Live Server no front, curl, Postman ou Insomnia), sem cabeçalho de autorização. Onde o backend precisa saber "quem" executa a ação (auditoria, autoria de registros, mudança de categoria), o identificador é passado explicitamente como id_usuario em query string ou no corpo da requisição.
- **Autorização por perfil parcial:** alguns serviços ainda validam o perfil consultando o id_usuario informado (validarPerfil), mas, sem auth, esse id_usuario é fornecido pelo cliente e não é criptograficamente garantido.
- **Visibilidade do prontuário:** enquanto não há auth, a listagem de registros de acompanhamento retorna sempre apenas os de visibilidade Publico_Equipe (escolha mais restritiva, para não expor dados sensíveis de Restrito_Psicologia). Os pontos exatos estão marcados com // TODO no código.
