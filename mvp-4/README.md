## 📝 Descrição

O Nexus é uma aplicação web desenvolvida para a Pulse Mais, organização sem fins lucrativos que capacita jovens de baixa renda em tecnologia por meio de aulas, mentorias, apoio psicológico e bolsas de estudo. O projeto nasceu de um problema concreto: as informações de mais de 1000 alunos e ex-alunos estavam dispersas em múltiplas planilhas separadas por projeto e ano, sem integração entre si, o que dificultava e aumentava a duração das análises estratégicas, gerava dependência da memória individual da equipe e compromete a capacidade da instituição de apresentar dados de impacto para parceiros e financiadores.

Para resolver isso, o Nexus funciona como uma Single Source of Truth (SSOT) da Pulse Mais, centralizando em um único ambiente toda a jornada do aluno: do cadastro e frequência nas aulas e eventos, ao registro de empregabilidade, certificados e acompanhamento psicológico. A plataforma atende a quatro perfis distintos, cada um com permissões e funcionalidades específicas.

O Gestor acessa um dashboard com indicadores consolidados de impacto: total de jovens ativos, empregados, concluintes e em risco de evasão, sinalizado automaticamente quando um aluno registra uma falta dentro de um mesmo módulo. Esses indicadores embasam decisões estratégicas e relatórios a investidores. Ele também tem acesso às métricas individuais de cada aluno e consegue enviar comunicados gerais. A Coordenadora atua no dia a dia da operação: registra frequências, acompanha a jornada individual de cada aluno, documenta conquistas de emprego e recebe alertas automáticos de evasão, além de poder visualizar todos os indicadores principais em um dashboard que contém os alunos ativos, a frequência média, o risco de evasão e a evolução da jornada. A Psicóloga acessa um prontuário digital exclusivo, com controle de acesso por perfil: gestores visualizam apenas um indicador geral de estabilidade, sem acesso ao conteúdo clínico. O Aluno tem um portal próprio onde consulta sua trajetória completa na Pulse Mais, atualiza dados de contato e acompanha os comunicados da equipe.

## Stack Tecnológica

A Nexus foi desenvolvida com uma stack web simples, organizada e adequada para uma aplicação com interface estática, API própria e banco de dados relacional.

- **HTML:** estrutura das telas e páginas da aplicação.
- **CSS:** estilização, responsividade e padronização visual da interface.
- **JavaScript:** interações do front-end e consumo dos fluxos da aplicação.
- **TypeScript:** tipagem e organização do código do back-end, aumentando a segurança durante o desenvolvimento.
- **Node.js:** ambiente de execução utilizado para construir o servidor da aplicação.
- **Express:** framework responsável pela criação das rotas, middlewares e endpoints da API.
- **PostgreSQL:** banco de dados relacional usado para armazenar as informações da plataforma.
- **Supabase:** serviço utilizado como infraestrutura para o banco PostgreSQL em nuvem.
- **Jest:** ferramenta de testes automatizados, utilizada para validar controllers, services, repositories, rotas e fluxos de integração.
- **pg:** biblioteca de conexão entre o back-end em Node.js e o banco PostgreSQL.
- **dotenv:** gerenciamento de variáveis de ambiente, como credenciais e configurações do banco.
- **cors:** configuração de acesso entre o front-end e a API.

## 📁 Estrutura de pastas

A estrutura do repositório foi organizada para separar documentação, interfaces, back-end, banco de dados e testes automatizados.

```text
g04/
├── assets/
├── documentos/
│   ├── assets/
│   ├── outros/
│   ├── rascunhos/
│   └── wad.md
├── src/
│   ├── view/
│   │   ├── aluno/
│   │   ├── coordenadora/
│   │   ├── gestor/
│   │   └── psicologa/
│   ├── config/
│   ├── controllers/
│   ├── database/
│   ├── middlewares/
│   ├── repositories/
│   ├── routes/
│   ├── services/
│   ├── test/
│   ├── index.html
│   ├── app.ts
│   ├── server.ts
│   ├── jest.config.ts
│   ├── package.json
│   ├── package-lock.json
│   ├── tsconfig.json
│   └── .env.example
├── .gitattributes
├── .gitignore
└── README.md
```

Na raiz do projeto, a pasta `assets/` reúne imagens e recursos gerais utilizados no README. A pasta `documentos/` concentra a documentação do projeto, incluindo o `wad.md`, documentos complementares, rascunhos e recursos visuais como diagramas, wireframes e imagens de apoio.

A pasta `src/` reúne o back-end da plataforma, organizado em rotas, controllers, services, repositories, middlewares, conexão com banco de dados, configurações e testes automatizados. A pasta `view/`, dentro do `src/` contém as interfaces da aplicação, separadas pelos perfis de uso: aluno, coordenadora, gestor e psicóloga. 

O arquivo `app.ts` configura a aplicação Express, registra middlewares, rotas e também inicializa o servidor quando executado diretamente pelos scripts do projeto. O `server.ts` funciona como um ponto de entrada alternativo para importar o app e subir o servidor. Os arquivos `package.json`, `package-lock.json`, `tsconfig.json` e `jest.config.ts` controlam dependências, scripts, TypeScript e testes. O `.env.example` apresenta as variáveis de ambiente esperadas. O `.gitignore` define quais arquivos e pastas não devem ser versionados, como `node_modules/`, `dist/`, arquivos `.env`, logs e relatórios de cobertura. Já o `.gitattributes` auxilia na normalização dos arquivos de texto dentro do Git.

As pastas `node_modules/` e `dist/` podem aparecer no ambiente local, mas não fazem parte da estrutura principal documentada: `node_modules/` é gerada após `npm install` e `dist/` é gerada após o build do TypeScript.

## 💻 Configuração para desenvolvimento e execução do código

Esta seção explica como preparar o ambiente local para instalar, configurar e executar a aplicação Nexus.

### Pré-requisitos

Antes de iniciar, verifique se as seguintes ferramentas estão instaladas no computador:

- **Visual Studio Code:** editor recomendado para visualizar, editar e organizar os arquivos do projeto.
- **Git:** ferramenta utilizada para clonar o repositório e versionar o código.
- **Node.js:** ambiente necessário para executar o back-end em JavaScript/TypeScript.
- **npm:** gerenciador de pacotes instalado junto com o Node.js.
- **Banco PostgreSQL/Supabase:** banco de dados utilizado pela aplicação para persistir as informações.

Também é recomendado ter acesso às credenciais do banco de dados do projeto, pois elas serão necessárias para preencher o arquivo `.env`.

### Passo 1 — Instalar o Visual Studio Code

O Visual Studio Code será utilizado para abrir a pasta do projeto, editar arquivos e executar comandos pelo terminal integrado. Caso ainda não tenha o VS Code instalado, acesse:

```text
https://code.visualstudio.com/
```

Baixe a versão correspondente ao seu sistema operacional e conclua a instalação.

### Passo 2 — Instalar o Git

O Git será utilizado para baixar o código do repositório. Caso ainda não tenha o Git instalado, acesse:

```text
https://git-scm.com/
```

Após a instalação, abra o terminal e verifique se o Git está disponível:

```sh
git --version
```

Se o terminal retornar a versão instalada, o Git foi configurado corretamente.

Exemplo de resposta esperada:

```text
git version 2.x.x
```

### Passo 3 — Instalar o Node.js

O Node.js permite executar o servidor do projeto. O npm, instalado junto com o Node.js, permite instalar as bibliotecas necessárias. Caso ainda não tenha o Node.js instalado, acesse:

```text
https://nodejs.org/
```

Recomenda-se utilizar uma versão atual do Node.js, preferencialmente a partir da versão 20. Após instalar, verifique as versões do Node.js e do npm:

```sh
node -v
npm -v
```

Exemplo de resposta esperada:

```text
v20.x.x
10.x.x
```

### Passo 4 — Clonar o repositório

Escolha uma pasta do seu computador para armazenar o projeto. Em seguida, abra o terminal nessa pasta e execute:

```sh
git clone https://git.inteli.edu.br/graduacao/2026-1b/t29/g04.git
cd g04
```

Caso o Git solicite autenticação, utilize suas credenciais de acesso ao GitLab/Inteli. Em alguns casos, especialmente ao clonar via HTTPS, pode ser necessário usar um **Access Token** no lugar da senha da conta. Esse token deve ser gerado no GitLab/Inteli e usado apenas como credencial de acesso ao repositório.

Depois do clone, abra a pasta `g04` no VS Code pelo menu:

```text
File > Open Folder
```

Dentro do VS Code, abra o terminal integrado e confirme que ele está apontando para a pasta do projeto. O caminho exibido no terminal deve terminar em `g04`.

### Passo 5 — Instalar as dependências

O código da aplicação (incluindo o `package.json`) fica na pasta `src/`. Por isso, antes de instalar as dependências, entre nessa pasta:

```sh
cd src
```

Todos os comandos `npm` dos próximos passos (`npm install`, `npm run migrate`, `npm run dev`, `npm test` e `npm run build`) devem ser executados de dentro da pasta `src/`.

Em seguida, instale as dependências:

```sh
npm install
```

Esse comando instala todas as dependências necessárias para executar a aplicação, incluindo Express, TypeScript, Jest e o driver `pg` para conexão com PostgreSQL. Ao final, uma pasta `node_modules/` será criada automaticamente.

Se o comando terminar sem mensagens de erro, a instalação foi concluída.

### Passo 6 — Configurar as variáveis de ambiente

O projeto usa variáveis de ambiente para guardar configurações sensíveis, como dados de conexão com o banco. Crie o arquivo `.env` a partir do arquivo de exemplo:

```sh
cp .env.example .env
```

No Windows, caso o comando acima não funcione no terminal utilizado, execute:

```sh
copy .env.example .env
```

Depois, abra o arquivo `.env` e preencha as credenciais reais do banco PostgreSQL/Supabase. A opção recomendada é utilizar:

```env
DATABASE_URL=postgresql://postgres:SENHA_DO_BANCO@HOST_DO_BANCO:5432/postgres
DB_SSL=true
```

Também é possível configurar o banco usando variáveis separadas:

```env
DB_HOST=HOST_DO_BANCO
DB_PORT=5432
DB_NAME=postgres
DB_USER=postgres
DB_PASSWORD=SENHA_DO_BANCO
DB_SSL=true
```

O arquivo `.env` não deve ser enviado para o Git, pois contém informações sensíveis.

Se você ainda não tiver acesso ao banco de dados, o servidor pode até iniciar, mas as rotas que dependem do banco e o comando de migração não funcionarão corretamente.

### Passo 7 — Executar as migrações do banco

Com o `.env` configurado, execute:

```sh
npm run migrate
```

Esse comando cria ou atualiza as tabelas necessárias no banco de dados, de acordo com os scripts de migração do projeto.

Se o comando exibir mensagens de erro relacionadas a senha, host ou SSL, revise as informações preenchidas no arquivo `.env`.

### Passo 8 — Rodar o projeto localmente

Para iniciar a aplicação em modo de desenvolvimento, execute:

```sh
npm run dev
```

Esse é o comando principal para rodar o projeto localmente. Ele executa o `app.ts` com recarregamento automático durante o desenvolvimento.

Enquanto estiver usando a aplicação no navegador, mantenha esse terminal aberto. Se o terminal for fechado ou o processo for interrompido, a aplicação deixará de responder.

Quando o servidor iniciar corretamente, o terminal deverá exibir uma mensagem semelhante a:

```text
Servidor rodando na porta 3000
```

Por padrão, a aplicação ficará disponível em:

```text
http://localhost:3000
```

Ao acessar a rota principal, o servidor redireciona para a tela de login:

```text
http://localhost:3000/login.html
```

Também é possível verificar se a API está rodando pela rota:

```text
http://localhost:3000/health
```

Para verificar a conexão com o banco de dados, utilize:

```text
http://localhost:3000/health/db
```

Para parar o servidor local, volte ao terminal onde o `npm run dev` está rodando e pressione:

```text
Ctrl + C
```

### Acesso à plataforma (credenciais de teste)

Com o servidor em execução e o banco populado com os dados de teste, acesse `http://localhost:3000/login.html`. Na tela de login:

1. Selecione o **Perfil de acesso** desejado (Aluno, Coordenadora pedagógica, Gestor ou Psicóloga);
2. No campo **"E-mail, RA ou RM"**, informe o **RA** (no caso do aluno) ou o **RM** (nos demais perfis);
3. Informe a **senha** correspondente e clique em **Entrar**.

A senha de cada usuário segue o padrão `Nexus@<número>`, em que `<número>` é o próprio RA/RM do usuário. As faixas de identificadores provisionados para cada perfil são:

| Perfil | RA/RM (a partir de) | Padrão de senha | Exemplo de acesso |
|---|---|---|---|
| Aluno | 101 | `Nexus@<RA>` | RA `101` · senha `Nexus@101` |
| Coordenadora | 1001 | `Nexus@<RM>` | RM `1001` · senha `Nexus@1001` |
| Gestor | 2001 | `Nexus@<RM>` | RM `2001` · senha `Nexus@2001` |
| Psicóloga | 3001 | `Nexus@<RM>` | RM `3001` · senha `Nexus@3001` |

Os identificadores seguem em sequência a partir do valor inicial (por exemplo, alunos `101`, `102`, `103`…), e cada usuário tem como senha a palavra `Nexus@` seguida do seu próprio número. Também é possível entrar utilizando o e-mail cadastrado no lugar do RA/RM.

### Passo 9 — Rodar os testes

Para executar os testes automatizados, utilize:

```sh
npm test
```

Para gerar o relatório de cobertura dos testes:

```sh
npm run test:coverage
```

### Passo 10 — Executar a versão compilada

Opcionalmente, para gerar a versão compilada em JavaScript e executar uma versão de produção local, utilize:

```sh
npm run build
npm start
```

Nesse fluxo, o `npm run build` gera a pasta `dist/` e o `npm start` executa o arquivo compilado `dist/app.js`.

### Problemas comuns

Se o comando `git --version`, `node -v` ou `npm -v` não for reconhecido, feche e abra o terminal novamente. Caso o problema continue, reinstale a ferramenta correspondente e verifique se ela foi adicionada ao PATH do sistema.

Se o `npm install` falhar, confirme que o terminal está dentro da pasta `g04` e tente executar o comando novamente. Também vale verificar se a conexão com a internet está ativa.

Se a aplicação não abrir em `http://localhost:3000`, confira se o terminal ainda está executando o `npm run dev`. Caso a porta `3000` já esteja em uso, encerre o processo antigo ou altere a porta no arquivo `.env` usando a variável `SERVER_PORT`.

Se a rota `/health` funcionar, mas `/health/db` retornar erro, o servidor está rodando corretamente, porém a conexão com o banco precisa ser revisada no arquivo `.env`.

    * Desenvolvimento básico do projeto: definição do minimundo, personas, user stories, requisitos funcionais e não funcionais, regras de negócio, casos de uso e matriz inicial de rastreabilidade.

    * Segunda versão funcional da aplicação web: desenvolvimento do front-end, integração com o back-end, fluxos principais ponta a ponta, suíte de testes automatizados da WebAPI e atualização da arquitetura, banco de dados, endpoints e rastreabilidade no WAD.
* 5.0.0 - 26/06/2026
    * Entrega final do projeto: realização de atualizações pontuais, correções de bugs e ajustes na aplicação com base nos feedbacks obtidos durante os testes de usabilidade.
